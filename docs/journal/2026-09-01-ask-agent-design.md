# sumac: Local In-Process Agent for `sumac ask`

**Status:** design record, drawn from an external ideation session; implementation not started
**Author:** drafted with Claude, 2026-09-01
**Scope:** new `sumac/llm.py` (or equivalent), `cli.py`'s `ask` command, no changes to `decide.py`/`ledger.py`/`events.py` domain logic

---

## 1. Motivation

The domain model (event log, ledger fold, `decide` gate) is already correct and already tested against a real household's usage. The friction is entirely at the interface: a single physical action — "take a ragu out of the freezer and a tin of tomatoes out of the pantry, put ragu-for-one and a jam jar of tomatoes in the fridge, second shelf" — decomposes into several `sumac add` invocations, each requiring information the user must look up by hand first: the exact product string as stored (`"Homemade Ragu"` vs `"Home Made Ragu"`, two distinct products), the exact location id (`fridge-main-shelf-2`, not "second shelf"), and the exact unit already on record (`bags`, not `bag` — `decide_change` rejects the singular with `unit_unconvertible` since unit conversion is nominal per `Config.convert`, not a pluralisation rule). A worked session doing exactly this — recorded in full below in §2 — took thirteen commands and three dead-end attempts to complete a task a person would describe in one sentence.

The session's own conclusion, reached before any code existed, is the thesis this entry inherits: the CLI's command surface is a fine *domain API* and a poor *human interface* for compound, underspecified requests. The fix is not to make the CLI's argument parsing smarter — `sumac add`'s job is to be an unambiguous, scriptable operation, and it should stay that way — but to add a second, narrower entry point that accepts an underspecified sentence, resolves it against the real inventory, and asks before writing anything.

## 2. How the idea developed

The starting point was a real interactive session (transcript preserved in this repo's chat history, not reproduced verbatim here) in which the user asked an external LLM, command by command, how to record that a jar of jam was eaten, then how to execute the ragu/tomatoes compound request above. That session surfaced two facts that shaped everything after it:

- **The chore was real and specific, not a vague UX complaint.** `sumac find` already returns exactly the disambiguating information a human needs (product name, quantity, unit, full location path) — the burden was manually transcribing that output back into `sumac add`'s positional arguments, correctly, every time.
- **The compound request was not a `movement`.** The ragu was cooked from frozen base ragu and repackaged into a Tupperware box under a new name ("ragu for one"); the tomatoes were decanted from a half-used tin into a jam jar. Both product identity *and* unit changed. The session's own resolution was two `consumption` events (against the original products, from their original locations) followed by two `discovery` events (the new products, into the fridge) — four writes, not one `movement` with a relabelled endpoint. This is the shape any agent built for this domain has to reproduce: **one user utterance can require an ordered sequence of distinct domain operations**, not a single tool call.

From there the design question moved through several rejected shapes, each rejected for a stated reason rather than by default:

- **A rewritten, "smarter" `sumac add`** (inferring source location from a unique `find` match, accepting plurals, taking a free-text destination like "fridge second shelf") — rejected as the first idea, because it still requires the human to decompose a compound request into separate CLI invocations; it improves each command without addressing the ragu/tomatoes case at all.
- **A general chat/GUI product** (conversational history, a `sumac` REPL with a chat transcript, eventually a web UI with a command palette) — the broader idea explored the shape of this at length, but it was set aside as out of scope for a first slice: it multiplies the surface area (rendering, session state, undo) before the core translation — sentence to domain calls — is shown to work at all.
- **Ollama** — rejected as a dependency: it runs as a separate local server process, which conflicts directly with the constraint that `sumac ask` is a plain CLI invocation with no daemon and no network port, local or otherwise.
- **`llama-cpp-python`** — considered viable (in-process, CPU-capable, GGUF, has tool-calling support) and not rejected, but superseded once mistral.rs's Python SDK was found to offer the same shape with a tool-callback API already built around exactly this pattern.
- **mistral.rs's `mistralrs serve --agent`** — this was the one genuine near-miss, because the documentation page found for it (`docs/agents/build-an-agent`) is titled "agents" and looked at first glance like the intended entry point. It is not: that mode runs a server process (`mistralrs serve`) and hands the model a fixed, generalist toolset — web search, arbitrary Python execution, shell execution — none of which sumac's domain permits an LLM to touch. Distinguishing this from the Python SDK's *in-process* agentic callback API (`examples/python/agentic_tools.py`, quoted in full in the originating request) is the pivot the design settled on.
- **LangChain, CrewAI, MCP, or any other agent-orchestration framework** — rejected throughout on the same grounds: the tool surface is fixed at roughly five typed Python functions, and the loop that dispatches a tool call and feeds back its result is exactly what mistral.rs's `Runner.tool_callbacks` + `max_tool_rounds` already does, in-process, with no added framework.

## 3. What this is

`sumac ask "<sentence>"` is a CLI command, alongside the existing ones, that:

- Loads a small GGUF instruct model (roughly 0.6B–1.7B parameters, chosen for CPU inference speed over raw capability — the model's job is narrow semantic parsing against a five-tool vocabulary, not general reasoning) via mistral.rs's Python `Runner`, in-process, inside the same Python interpreter running the CLI. No server, no port, no daemon left running after the command exits.
- Registers a small, fixed set of Python tool callbacks on that `Runner` — not the CLI's own commands, but thin wrappers around the domain layer's existing entry points (`ledger.build_inventory` for search/lookup, `decide.decide_change` for consumption/movement/discovery, `decide.decide_correct` for corrections). Registered via `Runner(..., tool_callbacks={...})` and driven with `max_tool_rounds` set on the `ChatCompletionRequest`, per the SDK example that motivated this design — the engine executes the loop of "model proposes a tool call → sumac's Python code runs it → the result is fed back to the model" without any additional orchestration code.
- Can and is expected to produce **more than one domain call per invocation** — the ragu/tomatoes case (§2) is the reference example: one sentence, four writes (two `consumption`, two `discovery`), each going through the same `decide_change` gate `sumac add` uses today. The agent's role is to plan and sequence those calls, not to reimplement or bypass what `decide_change` already validates.
- Searches before acting: given "take a ragu out of the freezer," the tool wrapping inventory lookup is called first, and its actual result (the real matching products, quantities, units, and locations — not anything the model asserts on its own) is what the model reasons over for the next tool call. This mirrors `sumac find`'s existing output exactly; the agent is not given a dump of the whole inventory, only what a query returns.
- Asks the user to disambiguate rather than guessing, when a search returns more than one plausible match with no basis in the sentence for picking one — the stated example being `find_inventory("ragu")` returning both "Home Made Ragu" (1 bag) and "Homemade Ragu" (7 bags): the agent presents both and stops rather than choosing.
- Surfaces the same domain errors `sumac add` would produce — `unit_unconvertible`, `unknown_location`, `missing_endpoint`, and the rest of the rejection catalogue in `docs/journal/2026-08-30_decide-pattern-data-integrity-upgrade.md` §4 — back to the model as a tool result, not as a crash, so the model can retry with a corrected call or explain the failure to the user rather than the process exiting on an unhandled exception.

## 4. What this is not

- **Not a replacement for the existing CLI.** `sumac add`, `sumac find`, `sumac status`, and every other command are unchanged and remain the deterministic, scriptable path — the point of `mv`-style commands (fully specified by their arguments, no interpretation required) is precisely that they do not need a confirmation step, and nothing about adding `ask` changes that property for the rest of the CLI.
- **Not the mistral.rs generalist agent mode.** `mistralrs serve --agent`'s built-in web-search, shell, and Python-execution tools are explicitly not used. The LLM's only capabilities are the specific typed functions sumac registers; it has no path to the filesystem, the database, or arbitrary code, satisfying the constraint that the domain layer stays authoritative and the model can only invoke what is explicitly exposed to it.
- **Not a chat product.** The interaction is one request in, one proposed action (or one clarifying question) out, then either confirmation or cancellation — not a persisted multi-turn conversation with history that itself becomes a feature. `sumac`'s existing model deliberately does not track chat history between calls (matching mistral.rs's own note that its `Runner` does not track chat history across separate `send_chat_completion_request` calls) — each `sumac ask` invocation is independent.
- **Not a source of new domain rules.** Every operation the model can trigger already exists in `decide.py`. Nothing about this design adds a new `ChangeKind`, a new event type, or a new validation path — the "discovery" and "consumption" events used in the ragu/tomatoes example (§2) are the existing `discovery` and `consumption` kinds `sumac add` already accepts, invoked in sequence rather than added to.
- **Not restricted to interactive human use.** `sumac ask` is a CLI command like any other and can be driven by a script or by another agent, not only typed at a terminal by a person. The propose-then-confirm behaviour described in §5 belongs to the interactive path; a non-interactive caller (a script, a cron job, another agent) is a different consumer of the same underlying "sentence in, proposed writes out" mechanism and owns its own decision about whether and how to gate execution — this design does not assume a human is always the one pressing confirm.

## 5. Why a confirm step, and why only here

Every other sumac command is unambiguous by construction: `sumac add consumption "Strawberry Jam" 1 jar --from fridge-door` fully determines what will be written before it runs, the same way `mv a b` fully determines the filesystem operation before it runs — there is nothing to interpret, so there is nothing to confirm. `sumac ask` is different in kind, not degree: the input is a sentence that requires interpretation — resolving "a ragu" against two candidate products, resolving "second shelf" against a location id, deciding that "a jam jar full of tomatoes" describes a new product-and-unit pair rather than a straight move — before it can become a determinate operation at all.

That interpretation step is exactly where a small model can be wrong in a way `sumac add`'s argument parser cannot: parsing `"1"` as an amount has one meaning, but resolving "the ragu" against inventory has several. The proposal is therefore: `sumac ask` resolves the sentence into a concrete, fully-specified sequence of the same writes `sumac add` would produce, shows that sequence to the user before any of it is written (mirroring the search-first, ask-when-ambiguous behaviour in §3), and only calls into `decide_change`/`store.append` after the user accepts it. This keeps the domain layer's guarantees intact — every write, agent-proposed or hand-typed, passes through the identical `decide_change` gate — while adding a review step at the one point in the system where the input itself is ambiguous rather than the operation.

## 6. What is not yet decided

- The exact tool function signatures (parameter shapes for search/consume/move/discover) and how closely they mirror `decide.decide_change`'s existing keyword-argument shape versus a narrower agent-facing wrapper.
- How the proposed write sequence is rendered to the user for confirmation — plain text, a rich table via `render.py`, or output shared with `sumac doctor`'s existing anomaly-table rendering.
- Which specific GGUF model and quantisation is used by default, and where the model file is expected to live on disk (a cache directory under `paths.py`'s existing layout, or left to mistral.rs's own Hugging Face cache resolution).
- Whether `sumac` with no arguments becomes an interactive agent REPL, deferred in the originating request until `sumac ask` itself is proven.
- Test strategy for the agent loop without invoking a real model — the originating request calls for separating orchestration (sequencing tool calls, applying writes, rendering the proposal) from inference (the actual `Runner` call), so the orchestration can be driven by a fake model/fake tool-call sequence in tests.

## 7. How mistral.rs's Python SDK actually structures agentic tool use

Checked directly against two sources rather than assumed: the type stub shipped in the installed package (`.venv/lib/python3.12/site-packages/mistralrs/__init__.pyi`, version 0.9.2, matching this repo's pinned dependency) and the upstream docs and examples at `EricLBuehler/mistral.rs` on the `master` branch, fetched fresh rather than recalled from the originating request's pasted excerpts.

**Two distinct loops, named as such by the docs themselves** (`docs/src/content/docs/guides/agents/tool-calling-basics.mdx`, "The two modes"):

- **Client-side loop.** The model emits `tool_calls`; the caller runs the tool itself and sends the result back as a new `{"role": "tool", ...}` message in a second `send_chat_completion_request` call. Demonstrated in `examples/python/tool_call.py`, which calls `send_chat_completion_request` twice, manually appending both the assistant's tool-call message and the tool's result between calls.
- **Server-side loop.** mistral.rs runs the entire round-trip — inference, tool execution, feeding the result back, repeating — inside one `send_chat_completion_request` call. Demonstrated in `examples/python/agentic_tools.py` and `examples/python/custom_tool_call.py`, both of which register a `tool_callbacks` mapping on `Runner` and set `max_tool_rounds` on the request.

Both loops are real, current, and documented; "server-side" is the project's own name for this mode even in the Python SDK, where there is no literal server — it means "mistral.rs's own runtime drives the round loop," matching the same code path the HTTP `mistralrs serve --agent` mode uses. The distinction drawn in §2 above (in-process SDK agentic callbacks vs. the `mistralrs serve --agent` HTTP mode) is a different axis from this one — client-side vs. server-side loop is about *which loop drives the tool-call/result cycle*, and is orthogonal to *whether that loop runs in-process or over HTTP*. Both loops are equally in-process when driven through `Runner`; the server-side loop is the one that additionally needs `tool_callbacks` registered so mistral.rs has something to call.

**The server-side loop engages only when specific request conditions hold** (`agentic-runtime.md`, "How the loop runs"): `web_search_options` set, a `code_interpreter`/`shell` tool entry with the corresponding executor enabled, **"The request carries `tools` and server-side executors exist for them (SDK `tool_callbacks` or connected MCP tools)"**, `max_tool_rounds` set, or a `--tool-dispatch-url` configured server-side. For sumac, registering `tool_callbacks` on `Runner` and setting `max_tool_rounds` on the request both independently satisfy this — belt and braces, and consistent with every server-side-loop example in the repo, which sets both.

**Exactly one tool call executes per round, even if the model asks for several.** `agentic-runtime.md` states this plainly, as a numbered step in the loop description: "The tool is executed through one of the paths above... If the model returns more than one tool call, only the first is executed and a warning is logged." This is load-bearing for sumac's compound-request case (§2's ragu/tomatoes example): a model that emits four tool calls in one turn — hoping to consume the ragu, consume the tomatoes, discover ragu-for-one, and discover the tomato jar all at once — would have three of those four silently dropped, with only a log warning on mistral.rs's side. Getting all four writes to happen requires the model to make them across four separate rounds, each one seeing the previous round's result before deciding the next call — which is also how the loop is designed to work (step 6: "the message history is extended with the assistant's tool-call message and a `tool`-role response, so the next inference pass sees the outcome"). Two consequences for the design in §3/§9 below: `max_tool_rounds` must be sized for *one tool call per round, sequential*, not for "how many distinct actions this request needs" — the ragu/tomatoes example needs at minimum six rounds (two `find_inventory` calls plus four writes) before the model's final free-text reply, so a cap in the low single digits would truncate a real compound request without any error, only an incomplete result.

**`agent_permission` / `agent_approval_callback` gate registered `tool_callbacks`, not only mistral.rs's built-in tools.** `permissions-and-approvals.mdx` states the scope directly: "`agent_permission` controls whether mistral.rs may run an agent action after the model asks for one. It applies to all server-executed actions, not just Python: code execution, shell, web search, file tools, **registered callbacks**, and external tool dispatch." The only worked Python example (`examples/python/code_execution_approval.py`, also reproduced in the docs page's Python tab) demonstrates the mechanism against the built-in code-execution tool rather than a custom `tool_callbacks` entry, but the documented scope is explicit that it is the same mechanism for both. The callback receives an `AgentToolApproval` (`approval_id`, `session_id`, `round`, `tool: AgentToolMetadata` carrying `source`/`kind`/`label`, `arguments_json`, and a convenience `.arguments()` parse method) and returns `True`, `False`, or an `AgentToolApprovalDecision` (`.approve(remember_for_session=...)` / `.deny(message=...)`) — all present in the installed 0.9.2 stub (`AgentPermission`, `AgentToolApproval`, `AgentToolApprovalDecision`, `AgentToolMetadata`, `AgentToolSource`, `AgentToolKind`).

**`function.strict: true` constrains tool-call argument decoding; `grammar`/`grammar_type` constrains the final assistant message.** These are two separate mechanisms, not variants of one. `tool-calling-basics.mdx`'s "Strict tool calling" section: with `strict: true` on a tool's `function` object, "mistral.rs constrains the generated arguments to the tool's `parameters` JSON Schema during decoding... Non-strict tools are only parsed as JSON after generation completes, so malformed output can still appear." Built-in tools are strict by default; custom function tools are not, unless the schema sets it explicitly — every custom-tool example in the repo that defines its own function (`tool_call.py`, `agentic_tools.py`) sets `"strict": True` in the schema dict by hand. Separately, `grammar_type="json_schema"` plus a `grammar` JSON string constrains the assistant's own text output to a schema (`examples/python/pydantic_schema.py`, using `Fleet.model_json_schema()`; `examples/python/json_schema.py`, using a hand-written schema) — this is a `ChatCompletionRequest` field pair unrelated to `tool_schemas`/`tool_choice`, useful for structured final answers, not for tool-call arguments.

**The docs' own stated first preference for custom tools is MCP, not SDK callbacks.** `tool-calling-basics.mdx`: "For custom tools, the cleanest path is to run them as an MCP server and connect mistralrs as a client... The SDKs can also register custom callbacks directly: Python uses `Runner(tool_callbacks=...)`." Sumac's scope constraints (§ "Important scope constraint" in the originating request) explicitly rule out MCP. Recorded here so the design in §9 below is understood as picking the documented alternative to the maintainers' first-choice pattern, not as having missed it — `Runner(tool_callbacks=...)` is the correct in-process mechanism given that constraint, not merely *a* mechanism among equally-preferred options.

**The Python `ToolChoice` enum, as installed, has exactly two members.** `mistralrs/__init__.pyi`: `class ToolChoice(Enum): NoTools = "None"; Auto = "Auto"`. `tool-calling-basics.mdx`'s "Forcing or suppressing tool use" section documents additional `tool_choice` shapes — a named-function force, `"required"`, and `{"type": "allowed_tools", ...}` — but `ChatCompletionRequest.tool_choice` is typed `ToolChoice | None`, and the Python enum offers no constructor for those variants. Those shapes are demonstrated in the docs only for the HTTP/OpenAI-SDK/Rust surfaces (`tool-calling-basics.mdx`'s "Allowed Tools Examples" tabs show Python only via the *HTTP-facing* `openai` client, not the `mistralrs` Python SDK). Concretely: forcing the model to call `find_inventory` before it is allowed to answer, or restricting a given round to a named tool, is not reachable through the Python SDK's `tool_choice` field in 0.9.2 — only `Auto` (model decides) or `NoTools` (disabled) are available from Python. Steering "search before acting" (§3) is therefore a prompting concern, not an API-enforced one, for this SDK surface.

## 8. Is `AgentRunner`, as committed, the idiomatic shape?

Partially. The class-shaped wrapper itself is reasonable and matches how every example in §7 is structured: construct one `Runner` with `tool_callbacks` registered up front, closed over whatever state the callbacks need, then issue one `ChatCompletionRequest` per user turn against it. `cli.py`'s `AgentRunner(data_dir, key)` follows that shape at the construction boundary — `data_dir`/`key` are exactly what sumac's tool callbacks would need closed over to call into `ledger`/`decide`/`config`, and building the `mistralrs.Runner` once per `AgentRunner` (rather than once per tool call) is the right granularity given the getting-started guide's own note, quoted in the originating request, that a `Runner` should be "reuse[d]... for the lifetime of the process to avoid reloading."

Two parts of the committed shape are not idiomatic, for reasons grounded in §7 rather than style preference:

**1. `.run(prompt) -> str` gives no seam for the confirm step §5 requires, and per §7's server-side-loop mechanics, there may be no way to add one after the fact.** If `.run()` returns a single string and the CLI's only remaining step is `render.print_success(result)` (cli.py:398), the actual domain writes — the `decide.decide_change`/`store.append` calls a tool callback would make for `consume_inventory`/`move_inventory`/`discover_inventory` — must already have happened *inside* `.run()`, before it returns. But §7 established that the server-side loop executes each registered callback synchronously, one at a time, as soon as the model asks for it (or as soon as `agent_approval_callback` approves it, if permissioning is used) — there is no mode in which `send_chat_completion_request` collects every tool call the model would like to make across a whole session and hands them to the app as a batch before any of them run. A `.run()` returning one final string is only coherent if every write already committed one-by-one as the model proposed each one — which forecloses §5's "propose the whole plan, review it, then commit" behavior at the type-signature level, not just as an unfinished detail. Whatever confirmation mechanism sumac adopts has to be wired into the same call that runs the loop (see §9), not layered on afterward around a `str` return.

**2. `.run() -> str` discards `ChatCompletionResponse.agentic_tool_calls`.** The 0.9.2 stub declares `agentic_tool_calls: list[AgenticToolCallRecord] | None` on `ChatCompletionResponse`, populated by the server-side loop — one entry per round, carrying `round`, `name`, `arguments`, `result_content`. This is exactly the structured trace a confirmation UI, a `sumac ask --verbose` flag, or `render.py`'s existing table-building functions would want (`render.print_log`, `render.print_doctor` both render structured per-record tables today, not prose). Collapsing the response to `choices[0].message.content` before it reaches `cli.py` throws that trace away before the CLI layer ever sees it exists.

**3. Naming, minor.** `sumac.llm.AgentRunner` wraps a `mistralrs.Runner` under a name that differs by one word, inviting the reader to wonder whether it *is* one (subclass) or *holds* one (composition) without reading the implementation. Not load-bearing, noted for whoever writes `llm.py`.

None of this is a claim that `Runner(tool_callbacks=...)` itself, or a per-request `ChatCompletionRequest`, is the wrong mistral.rs primitive — §7 supports both as the documented, current, idiomatic mechanism for in-process custom tools. The critique is scoped to the thin wrapper `cli.py` already assumes exists (`AgentRunner(data_dir, key).run(prompt) -> str`), not to the underlying library usage that wrapper would presumably call into.

## 9. Recommended shape

Design-level only — no code follows from this section; `cli.py` is unchanged by this entry, per instruction.

**Confirmation mechanism: `agent_permission=AgentPermission.Ask` with a `agent_approval_callback` sumac supplies, rather than staging writes and asking once at the end.** §7 established that `agent_permission`/`agent_approval_callback` is documented to cover registered `tool_callbacks`, and it is the one piece of this problem mistral.rs already implements — the pause/resume bookkeeping around "ask before running this specific action" is the library's, not sumac's, to build. The callback would auto-approve `find_inventory` (read-only, matches §3's "search before acting" requirement — no reason to interrupt a lookup) and, for `consume_inventory`/`move_inventory`/`discover_inventory`, render `call.arguments_json` (or the parsed form via `call.arguments()`) as a human-readable line — product, quantity, unit, location — before asking. `AgentToolApprovalDecision.approve(remember_for_session=True)` gives an escape hatch matching the CLI approval example's own `"a"`/"always" option, letting a user fast-forward through the remaining writes in one compound request after confirming the first.

This is an explicit, acknowledged departure from §5's original sketch of one holistic preview covering the whole proposed transaction before any of it commits: what mistral.rs provides natively reviews each write in sequence, as the model proposes it, not the full batch upfront. The alternative that would preserve the original sketch exactly — mutating tool callbacks that only stage a proposed write (accumulated in a list the closure owns) without calling `store.append`, letting the whole tool-calling loop run to exhaustion untouched, then presenting the accumulated list once and replaying it for real only after a single confirm — was considered and set aside for this entry's recommendation, not because it is unworkable, but because it needs sumac to build bookkeeping mistral.rs doesn't provide: later tool calls in the same run (a second `find_inventory` checking whether an earlier proposed consumption already landed) would need to reason against a staged view — real inventory plus not-yet-committed proposed deltas layered on top — rather than `ledger.build_inventory`'s real result, or the model could reason from stale figures mid-plan. The per-call approval path avoids that because every approved write commits for real immediately, so every subsequent tool call already sees the true state. Recorded here as the rejected alternative rather than omitted, since it is the more faithful match to §5's original design and a future entry may revisit the tradeoff once the per-call approval path has been tried against real requests.

**Tool schemas set `"strict": true`**, per §7's finding that custom function tools are not strict by default and every worked example that defines one sets it explicitly — material for a model in the 0.6B–1.7B range, where malformed tool-call JSON is a real failure mode the strict-decoding constraint removes outright rather than something sumac's own code would need to detect and recover from after the fact.

**`max_tool_rounds` sized for one write per round, not one round per compound request** — per §7's "only the first tool call in a round executes" finding, a cap needs headroom for *every* sequential search-then-act step a compound request could produce, not just "the number of distinct actions" — the ragu/tomatoes example needs at least six successful rounds before a final reply. A cap that is too low does not error; it silently stops the plan partway through, which is worse than an explicit rejection given §3's "never invent, never guess" requirement — a user seeing only two of four intended writes complete, with no error, is the anomaly-must-be-loud principle (`docs/journal/2026-08-30_decide-pattern-data-integrity-upgrade.md` §3.2) failing at the agent layer instead of the fold layer.

**Search-before-act, one-action-per-turn, and ask-when-ambiguous are prompt content, not request parameters** — per §7's finding that the Python SDK's `ToolChoice` enum cannot force a specific tool or require tool use, these behaviors (already specified in §3 above) have no API-level enforcement available from this SDK surface and must be carried entirely by a system-role message. This is worth stating plainly because it changes what "done" looks like for whoever implements this: the system prompt is not incidental scaffolding around the real mechanism, it *is* the mechanism for these three behaviors, and needs the same testing attention as the tool schemas themselves.

**Model loading: `Which.GGUF(quantized_model_id=..., quantized_filename=...)` over `Which.Plain(...) + in_situ_quant=...`** for this specific use case. Both are legitimate, current, documented loading paths (the latter is the getting-started guide's own primary example); the recommendation for sumac specifically is that `Which.GGUF` selects an already-quantized checkpoint, avoiding a full-precision download before local requantization — material for a model whose whole reason for being chosen is to be the small, CPU-only, always-resident option. `Which.GGUF`'s fields (`quantized_model_id`, `quantized_filename`, `tok_model_id`, `tokenizer_json`, ...) are present in the installed 0.9.2 stub.

**`session_id` left unset**, consistent with §4's existing "not a chat product" position and confirmed rather than merely asserted by this research: `agentic-runtime.md` describes `session_id` as being for continuity *across separate requests* ("message history, tool records, media, and code-execution state" surviving between calls) — a single `sumac ask` invocation makes one `send_chat_completion_request` call, and that call's internal multi-round loop does not need a `session_id` to function; the field exists to let a *future* multi-turn surface (§6's deferred `sumac` REPL) resume state between separate top-level calls, which is exactly the point at which sumac would need to start passing one.

## 10. Open questions surfaced by this research, not resolved by it

- Whether `AgentToolApprovalDecision.approve(remember_for_session=True)` has any effect within the internal rounds of a *single* `send_chat_completion_request` call made without an explicit `session_id` — the docs describe `remember_for_session` and `session_id` primarily in terms of cross-request continuity, and it is not confirmed here whether "remember" has a session to scope to for the length of one multi-round call if no `session_id` was passed into that call. Matters directly for §9's recommended use of `remember_for_session` as a fast-forward inside one compound `sumac ask` invocation — if it does not carry across that call's own internal rounds without a passed `session_id`, either `sumac ask` needs to mint an ephemeral `session_id` per invocation (in tension with the "not a chat product," no cross-invocation continuity position in §4/§9), or the fast-forward escape hatch does not work as sketched and each write in a compound request is asked about individually regardless.
- Whether a system-role message is accepted by mistral.rs's Python SDK the same way `user`/`assistant`/`tool` roles are in the fetched examples — inferred from OpenAI wire-format compatibility (every example's `messages` list follows that shape) rather than confirmed by a worked example containing one; none of the examples fetched for this entry happen to include a system message.
- Whether `agent_approval_callback`'s `AgentToolMetadata.kind` for a registered `tool_callbacks` entry is `AgentToolKind.Custom`, `.External`, or something else — the enum has both variants and no fetched example exercises the approval callback against a custom (non-built-in) tool to show which one a `tool_callbacks`-registered function actually reports.

## 11. Preview / dry-run mode, and why it is scoped to `sumac ask` alone

A separate requirement from §5's confirmation step: a mode that computes what `sumac ask` would do and never commits it, regardless of any answer a human would give — for inspecting or testing a request's interpretation without touching the vault at all. The originating request for this addition considered and rejected generalising this to every CLI command (a `--dry-run` flag on `sumac add`/`sumac snapshot`/etc.), on the grounds that producing the sequence of tool calls (`sumac ask`'s own job) is a separate concern from whether an individual already-fully-specified command like `sumac add` supports a dry run. That scoping is also the cheaper one to build: `decide.decide_change` and `decide.decide_correct` are already the seam a dry run needs, and already exist. `decide.decide_change` is documented as pure — "no I/O, no clock, no filesystem. State and config are arguments" (`docs/journal/2026-08-30_decide-pattern-data-integrity-upgrade.md` §3.5) — and confirmed structurally: it returns `tuple[list[Write], list[str]]` (decide.py:476-488) and touches neither `store` nor the filesystem anywhere in its body. The only place a `sumac add` invocation actually mutates anything is `cli.py`'s own `add` command, in the loop `for w in writes: store.append(data_dir, key, w.stream, w.obj)` (cli.py:264-265), *after* `decide_change` has already returned. A dry run for `sumac ask` therefore costs nothing at the domain layer: a mutating tool callback (`consume_inventory`, `move_inventory`, `discover_inventory`) calls `decide.decide_change` exactly as `cli.py`'s `add` command does today, and a dry run is simply the callback choosing not to take the second step — the `store.append` loop — that `cli.py` currently takes unconditionally. No change to `decide.py`, `store.py`, or any other CLI command follows from this. `sumac add` itself gains nothing and needs nothing.

## 12. Update to §9: preview-then-accept, not per-write approval, as the primary mechanism

§9 recommended `agent_permission=AgentPermission.Ask` with a per-tool-call `agent_approval_callback` as the confirmation mechanism, explicitly trading away §5's original "review the whole plan once" sketch because building that required a staged-inventory overlay (§9's rejected alternative) that mistral.rs does not provide. §11's dry-run mechanism removes the reason that alternative was rejected: it does not need a staged-inventory overlay, because in dry-run mode nothing commits at any point, so there is nothing for a later tool call in the same run to observe having changed. The dry run's whole point *is* to compute the plan without touching real state — the staged-overlay problem only mattered for the previously-considered version of that alternative, where writes needed to commit for real as soon as approved so that later tool calls saw a consistent live inventory. A dry run sidesteps that requirement by never committing at all, in either the approved or unapproved case, until a separate step after the model is no longer involved (§14).

**Revised recommendation: the whole-plan preview from §11 is the primary interaction, not `agent_approval_callback`.** The default (non-flag) `sumac ask "<sentence>"` invocation runs the agentic loop once in dry-run mode — `agent_permission=AgentPermission.Auto`, since nothing destructive is wired up regardless of permission mode when every mutating tool callback stops short of `store.append` — collects the resulting proposed plan, and only asks the human after the model has finished proposing, not before each individual write. `agent_permission=Ask`/`agent_approval_callback` is not required by this shape and is demoted from "the mechanism" to an optional defense-in-depth layer that could be added later around whatever eventually performs the real `store.append`; the default recommended design does not need it, because §14 has the human review the complete, already-fully-decided plan before any model or tool-callback code runs a second time.

This also moots, rather than answers, §10's first open question (`remember_for_session` without an explicit `session_id`): §14 mints an explicit `session_id` for other reasons (the feedback loop, §13), so a session unambiguously exists for the length of one `sumac ask` invocation regardless of what `remember_for_session` alone would or would not scope to — the design no longer depends on that question's answer.

## 13. Feedback and iterative revision

The requirement that prompted this update: after a preview, the human should be able to respond with more than accept or reject — free text describing what to change — and get back a revised plan, not just exit. Two ways to give the model that history were available from §7's research, and only one is a good fit:

**Rejected: sumac reconstructs the message history itself and resends the whole thing.** `ChatCompletionResponse` carries `agentic_tool_calls: list[AgenticToolCallRecord]` (round, name, arguments, result_content) but no `messages` field — the expanded per-round assistant/tool messages the server-side loop actually produced internally are not handed back to the caller. Rebuilding them well enough to append a correction and resend would mean sumac reconstructing tool-call IDs and message shapes for the model's own chat template, matching a wire format sumac does not own — the getting-started guide's "not a chat product" position (§4) is about not accumulating a *persisted* conversation across separate CLI invocations; it says nothing against a library-native mechanism for continuing one conversation within a single invocation's lifetime, and reconstructing that mechanism by hand duplicates something the SDK already does more reliably.

**Adopted: an ephemeral, per-invocation `session_id`.** `agentic-runtime.md`: "Use `session_id` when your app needs continuity across requests: message history, tool records, media, and code-execution state." `sumac ask` mints one `session_id` (e.g. `str(uuid4())`) when the command starts, holds it only in process memory, and passes it on every `ChatCompletionRequest` for the duration of that one invocation — never written to disk, never read back on a later `sumac ask` call, so the "not a chat product" position from §4 is preserved at the granularity that matters: no history persists *between* invocations, only *within* one. The feedback loop becomes: append the human's typed correction as a new `{"role": "user", "content": ...}` message, call `send_chat_completion_request` again with the same `session_id`, and let mistral.rs's session state supply everything the model already knows about the original request and what it already proposed — sumac does not need to re-explain any of it. Sumac's own accumulated-plan list (§14) is cleared before each such call: a revision replaces the previous proposal rather than appending to it, since the model is being asked to reconsider the whole plan, not extend it. A small cap on the number of feedback rounds (a fixed constant, not user-configurable in a first pass) avoids an unbounded back-and-forth with no natural stopping point.

## 14. Concrete interaction shape

Design-level only, in the same sense as §9 — no code follows from this section.

1. `sumac ask "<sentence>"` mints `session_id = str(uuid4())`, kept in memory only.
2. Sumac builds one `ChatCompletionRequest` — the system-role prompt from §9 plus the user's sentence, `tool_schemas` with `strict: true` per §9, `tool_choice=ToolChoice.Auto`, `max_tool_rounds` sized per §9's "one write per round" finding, `agent_permission=AgentPermission.Auto`, `session_id=session_id` — and calls `send_chat_completion_request`. Every mutating tool callback (`consume_inventory`/`move_inventory`/`discover_inventory`) calls the matching `decide.*` function against the real, current `ledger.build_inventory`/`config.build_config` state (so the plan reflects genuinely valid operations, warnings and all — a query that would raise `Rejected` still raises it here, surfacing the domain error to the model exactly as §3 already specifies) but does not call `store.append`; instead it appends the resolved call — which `decide.*` function, and the exact keyword arguments used to call it — to a plain list closed over by the orchestration layer, and returns a description of the resolved effect to the model as the tool result (so the model's own subsequent reasoning proceeds as if the write had happened).
3. When the call returns — the model produced a final reply with no further tool call, or `max_tool_rounds` was reached — sumac renders the accumulated list. An empty list (a read-only request like "where is the jam?") skips straight to printing the model's final text and exiting; there is nothing to accept or reject. A non-empty list is rendered as a structured plan — reusing `render.py`'s existing table-building style (`print_log`, `print_doctor`) rather than the single `print_success(str)` call `cli.py`'s current stub uses (§8).
4. For a non-empty plan, sumac prompts for one of: accept, reject, or free-text feedback.
   - **Reject**: print nothing further, exit 0, nothing written. The `session_id` is discarded with the process.
   - **Feedback**: clear the accumulated list, append the typed text as a new user message, call `send_chat_completion_request` again with the same `session_id`, and go to step 3 with the new response. Bounded by the round cap from §13.
   - **Accept**: for each resolved call recorded in step 2, in the same order, call the matching `decide.*` function *again* — same keyword arguments, but against a *freshly reloaded* `ledger.build_inventory`/`config.build_config` and a fresh `occurred_at=datetime.now(UTC)` — rather than replaying the `Write` objects computed during the dry run. Then `store.append` each resulting write, printing any messages `decide.*` returns exactly as `cli.py`'s `add` command already does (cli.py:262-263).
5. `--dry-run` (naming: the user's own "preview" and the more conventional Unix "dry run" name the same thing here, treated as synonyms in this entry) runs steps 1-3 only and exits — no accept/reject/feedback prompt, since there is nothing to act on the answer to. Useful non-interactively (no TTY to prompt against) and for iterating on a request's wording before ever risking a real commit.

Re-deciding on accept rather than replaying the dry run's `Write` objects verbatim is deliberate, not an oversight: `decide.decide_change`'s stock-shortfall handling (`docs/journal/2026-08-30_decide-pattern-data-integrity-upgrade.md` §3.5, "the shelf is authoritative, not the log") exists precisely to reconcile a decision against whatever the real holdings are *at commit time* — real time passes between a preview and an accept (at minimum, the time spent reading the preview; more if a feedback round happened), and something else could have changed the vault in between. Replaying stale `Write` objects computed during the dry run would bypass that reconciliation and could commit a `Counted` correction sized for inventory levels that no longer hold; re-invoking `decide.*` with the same arguments against current state gets the shelf-is-authoritative behaviour for free, the same way it already works for `sumac add`.

## 15. Limitations this design accepts rather than solves

- **A dry run's own tool calls do not see each other's not-yet-committed effects.** If a compound request's plan includes a second `find_inventory` search against a product or location an earlier step in the *same* dry run already proposed changing, that search still reads real, on-disk state — nothing was written, so there is nothing different for it to see. §9's rejected staged-inventory-overlay alternative would have solved this (and its counterpart for a live per-write-approval design), and remains available to build later if a real compound request is found to need it; it is not built for this entry's recommendation, on the grounds that no example so far (§2's ragu/tomatoes case included) actually re-queries a product it has already proposed changing within the same request.
- **A revision (§13) discards the previous proposal rather than diffing against it.** The human sees a full new plan after feedback, not a highlighted delta from the one before. Acceptable for a first pass; worth revisiting if compound requests commonly need several small corrections rather than one.
- **The feedback-round cap (§13) is unspecified** beyond "a small fixed constant" — no number is chosen by this entry.
